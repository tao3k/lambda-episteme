explanations the remaining source-labelled evidence can support. Its POO

* Structural risk scope

The shared risk is *instruction contamination before a valid signature*:
the signing authority may receive bytes that differ from the transaction
authorized by the legitimate decision makers. A cryptographic signature can
then be valid while the transfer is unauthorized. This risk is defined by the
trust boundary, not by a particular wallet product or intrusion route.

| Incident or model | Entry surface | What is established here | What remains a hypothesis |
|-------------------+---------------+--------------------------+---------------------------|
| Bybit 2025 | Human signing interface | Bybit reports a deceptive Safe interface and wallet logic change; NCC summarizes forensic findings about a compromised Safe developer machine. | Initial machine access, each signer's trusted display, and other production controls. |
| Bitget 2026 | Exchange hot/warm-wallet pipeline | Bitget reports unauthorized outflow; the CEO's preliminary backend explanation is reported separately. | Record mutation, API replay, queue injection, destination mapping, exact signer ingress. |
| Shared threat model | Candidate transaction before signing | Either entry class can be represented as a candidate that lacks an independently bound intent or display witness. | No particular candidate path is thereby proven to have occurred. |

Bybit's [[https://www.bybit.com/en/learn/this-week-in-bybit/bybit-security-incident-timeline][published timeline]] describes a disguised administrative transaction
that changed wallet contract logic before the drain. Its effect shape is
therefore different from a directly signed transfer. The Bitget update
does not identify which effect shape occurred internally. A chain-observed
outflow cannot by itself distinguish them.

The defensive cut is an independently authenticated, signer-side binding of
decoded transaction bytes to user intent, risk approval, ledger reservation,
display confirmation where applicable, wallet epoch, and a one-use nonce.
Cedar evaluates the bound request; the Host checks provenance and applies
the signing effect. The [[file:proof/tla/SigningIntentBoundary.tla][TLA+ model]] examines the temporal cut,
[[file:hypotheses.ss][Ascent]] compares possible ingress explanations, and
[[file:proof/lean/README.org][Lean-POO/Cedar]] replays policy revisions and a symbolic signing Host.
Their outputs have separate authority: a candidate route cannot authorize
a transfer, and a Cedar permit cannot authenticate a witness producer.

|---------------------+--------------------------+-------------------------------+-----------------------+------------------------------|

The backend variants above also have separate candidate topologies in
[[file:simulation.ss][the replay]]. These are adversary-capability models, not claims about
Bitget's implementation. The admin-change path can coexist with any ingress
mechanism; it is not a sixth mutually exclusive entry point. An observation
from a backend-controlled log is
provisional even if it matches a prediction. A separately admitted signer
record can narrow the queue hypothesis; a contradictory producer record must
remain visible. Neither a single matching signal nor a path in the graph
confirms an intrusion mechanism. The atomic tests demonstrate all three
outcomes without promoting a hypothesis to a fact or permit.

* Conditional path-family inference

The finer ingress candidates cannot yet be ordered from public data alone.
The broader *effect family* can be compared. [[file:hypotheses.ss][The Ascent family program]] joins each
published signal to the predictions and challenges of four families, then
aggregates distinct matched signals. A second reporter of the same signal
does not increase its match count. Its output is an auditable fit comparison,
not a statistical probability.

| Family | Published match | Missing or challenging observation | Current interpretation |
|--------+-----------------+-----------------------------------+------------------------|
| Backend-forged signed transfer | 5 of 5 modeled signals: backend compromise, spoofed data, wallet signature, cross-chain bursts, fixed gas limits | No authenticated signer ingress or decoded intent receipt | Best-supported family conditional on the cited reports |
| Backend administrative change then drain | Backend compromise and spoofed data | A linked on-chain wallet-control change is not in the supplied record | Still possible; operation path unresolved without a control-change receipt |
| Signer-interface administrative change | None of its distinguishing signals | No Bitget display/byte mismatch or linked control change has been supplied | Bybit mechanism remains a comparison, not the favored Bitget explanation |
| Private-key exfiltration | None | Bitget says its investigation ruled this out | Challenged by the current official account |

This ordering is at the effect-family level. The fixed gas limit pattern
favors an internal-transfer-shaped order over an ordinary customer withdrawal,
but does not reveal which backend component fabricated it. If the independent
gas analysis is removed, the effect-family model returns =undetermined=; if a
linked administrative effect is supplied instead, it selects the
administrative temporal path. The regression tests exercise both changes.

** Conditional ingress comparison

[[file:ingress-inference.ss][The separate ingress Case]] compares four possible backend entry surfaces through
Ascent relations. Its POO slots declare reported signals, independent
discriminators, hard challenges, and explicit model factors. Every factor hit
retains the signal and source that caused it; repeated reports of the same
signal do not multiply its weight. The output is a *model-relative support
share*, not an empirical probability that the actual intrusion used that
route. The four routes can also overlap in a real attack chain.

The illustrative architecture assumption is that the fixed gas pattern
identified by Bitquery is twice as compatible with an internal API or queue
operation as with mutation of an ordinary customer-withdrawal record or
destination map. Under equal starting weights, this gives API replay and
queue injection =2/6= each, versus record mutation and address-map
substitution =1/6= each. Removing that assumption makes all four tie at
=1/4=. A record mutation that enters an internal transfer worker would also
invalidate the assumption. No public signer-ingress record currently
distinguishes API from queue.

| Candidate ingress | Current model weight | Discriminating observation to obtain | Independent challenge |
|-------------------+----------------------+-------------------------------------+-----------------------|
| Internal API replay | 2/6 | Duplicate request identity in signer-owned ledger | Exact one-use request record |
| Queue injection | 2/6 | Orphan signer-ingress message | Verified producer chain |
| Withdrawal record mutation | 1/6 | Withdrawal with no authenticated matching intent | Exact authenticated intent |
| Address-map substitution | 1/6 | Destination differs from independently committed destination | Independent destination match |

The integrated replay emits these fractions only after all four route-specific
TLC counterexamples qualify. These fractions are conditional on the stated
factor and source reports;
they must not be presented as calibrated incident probabilities. A verified
duplicate signer request in a synthetic test changes the model weights to
=8:2:1:1=; an exact one-use signer record instead removes API replay from
that model. This sensitivity is the point of the comparison: the receipt
shows which evidence would change the ranking, while preserving uncertainty
about the real ingress.

* Fixture consequence reasoning

[[file:outcome.ss][The POO outcome algebra]] accepts Case-owned event rows through a =semantics=
slot. Its Ascent rules count a direct loss only when changed intent bytes,
a matching signature, and an independently observed outflow join on the
same transaction. For an administrative signing path, it also requires an
observed wallet-control change, ordering evidence, and a later linked drain.
A valid signature or public aggregate alone does not establish this chain.

| Synthetic branch | Supplied linked outflows | Derived fixture total | Missing-evidence counterexample |
|------------------+--------------------------+-----------------------+---------------------------------|
| Direct transfer | USD 30,000 + USD 45,000 | USD 75,000 | Removing the signature yields zero. |
| Administrative change then drain | USD 120,000 | USD 120,000 | Removing the observed control change yields zero. |

These are intentionally synthetic figures, separate from both exchanges'
reported losses. The [[file:../../../../../t/ontology/exchange-signing-outcome-test.ss][atomic outcome test]] checks the joins and missing-evidence
cases. An application must bind independent chain, signer, and ordering
receipts before these rows can support an incident conclusion.
When two observers report the same fixture transaction, the algebra counts
its amount once. Inconsistent amounts for that transaction fail closed
instead of producing an aggregate. Transaction identity, chain identity,
asset units, and valuation time still need an admitted deployment-specific
normalization before applying the same rule to real multi-chain evidence;
the synthetic USD rows are not an estimate of Bitget's loss.

* Temporal threat model and effect replay

[[file:proof/tla/SigningIntentBoundary.tla][SigningIntentBoundary.tla]] covers two effect shapes: a directly signed
transfer, and a signed administrative change that first grants wallet control
and permits a later drain. Preparation, signing, effect, independent outflow
observation, freeze, and recovery are distinct transitions. The abstract
model distinguishes the exact bytes and operation the user intended from the
apparently valid claims supplied to the signer. =WeakSign= trusts those claims;
=BoundSign= also requires independent intent, risk, ledger, and display
witnesses, exact bytes and operation, and a fresh nonce.

stateDiagram-v2

  Prepared --> Signed: WeakSign or BoundSign
  Signed --> Outflow: direct transfer effect
  Signed --> Controlled: admin-change effect
  Controlled --> Outflow: later drain
  Outflow --> Observed: independent receipt
  Prepared --> Frozen: emergency freeze
  Controlled --> FrozenControlled: freeze after control change
  FrozenControlled --> Outflow: existing control can still drain

=InterfaceAttackSpec=,

=DefendedSpec= uses =BoundSign=. The freeze after an administrative effect
cannot revoke control already applied; the model allows a later drain even
while the signer is frozen. This is a model counterexample to relying on a
signer-local freeze alone after the control change. [[file:proof/tla/README.org][The atomic qualification]]
requires Scheme parser acceptance and official TLC completion for the
defended finite state graph; nine attack configurations must yield the
expected invariant violation and transition sequence. The Lean companion
proves the listed finite replay cases. These results cover their bounded
models, not every possible deployed wallet behavior or a formal refinement
between TLA+ and Lean.

* Authorization boundary

The [[file:proof/lean/README.org][Lean-POO Exchange model]] composes intent, risk, ledger, signer,
incident freeze, and recovery policies and exports complete =.cedar= files
through Rust into [[file:proof/cedar/README.org][this Case's proof/cedar/]]. Cedar evaluates an admitted
request. The signer Host must bind
the exact payload bytes, chain, destination, amount, nonce, wallet epoch, and
independent attestations to that request, then apply an atomic effect gate.
If all claims come from one compromised backend, matching fields can still
pass a policy; the example includes this counterexample. Ascent candidates
guide investigation and freeze scope but never become =permit= facts.
The Lean/Cedar replay then tests independent controls, common-source claim
contamination, incident freeze, and premature removal of the freeze. It
also models an abstract signer Host: if it accepts Cedar =Allow= while trusting
backend-supplied claims, the attacker bytes reach a modeled signing effect;
requiring separately authenticated intent, risk, ledger, and display
witnesses blocks the same attempt. The Host replay also checks an
=admin-change= request whose digest labels agree but whose authenticated
intent witness says =transfer=: the Cedar claim passes, while binding the
operation type at the signer blocks the substituted effect. The model signs
no real bytes and submits
no wallet transaction.

* Scenario boundary

This directory carries the incident-specific source ledger, hypothesis
matrix, TLA+ model, and Lean-generated Cedar policy set. It contains no keys
or live exchange transactions. A downstream deployment must ingest its own
admitted records, check source independence, and replay the published Cedar
policy set through the POO Flow Host before any signer effect.
