#+title: Healthcare Scenario — relations, Temporal Causality, and assurance flow

* Enterprise purpose

=HealthcareScenario= is the vertical boundary.  A Case is one concrete
enterprise situation inside that boundary; a Profile is a reusable semantic,
Governance and authorization-capability slice selected by one or more Cases.
Profiles solve reuse and controlled change: evidence, privacy, care-context,
healing and medication-safety meaning can evolve independently, while each
Case receipt records the exact effective closure it admitted.

For the AI-assisted antibiotic prescription, the ordinary =case.ss= is the
selection and observation surface: it chooses Profiles and records the
reviewed clinical state.  The adjacent maintained =objects.ss= supplies a
native POO Case prototype with the default Cedar declaration, event and
trajectory slots, and relation graph.  Derivation uses ordinary POO slot
inheritance and override; there is no Case-specific evaluator or patch DSL.
The executable prescription Governance test checks both inherited slots and
the accepted/counterfactual admission paths.

The common Healthcare =base.ss= follows the same boundary: its ordinary
Profile chooses identity and policy values, while =base/objects.ss= maintains
the inherited concepts, relations, source and rule defaults.  This Profile
has no captured =self= governance method to rebind, so its inherited behavior
and downstream Medication Safety/Pharmacology Profiles remain unchanged.

* AI-assisted legacy Standard migration

The demand-loaded =au-legacy-interface-fhir-migration= Case implements one
bounded Australian migration path:
=HL7v2 2.5.1 ADT^A08 -> hl7.fhir.au.core@1.0.0 Patient=.  It does not resolve
=latest= and it does not imply that the separately declared CDA or national
service families are executable.

The AI assistant follows a typed, evidence-bound workflow:

1. inventory the exact legacy source snapshot and parser qualification;
2. normalize through the =gerbil-parser=-owned lossless HL7v2 artifact;
3. propose reviewed field mappings and identify every unmapped required field;
4. assess identity-collision, semantic-drift and parallel-interface risks;
5. generate an AU Core Patient candidate;
6. submit that candidate to the deterministic FHIR Provider;
7. explain conformance failures without changing the target edition;
8. bind an independent human review to the exact proposal digest;
9. recommend shadow validation and a phased cutover; and
10. request migration admission from the typed policy gate.

AI remains =advisory-only=.  Any AI authority escalation, unbound analysis,
unresolved required mapping, target-edition drift, missing human approval or
unbound conformance receipt fails closed.  Admission still does not authorize
cutover: the application owns that decision and retains the legacy source
snapshot and interface for rollback.

The Healthcare Migration Feature extends the core Standards Governance
Interface rather than adding an independent registry.  Its mandatory Slots are
=authority-provider=, =human-authorization=, =proof-assurance=,
=conformance= and =audit-receipt=. The Proof Module owns the TLA+/Lean
artifact, receipt, refinement and change-impact subgraph behind the single
mandatory =proof-assurance= binding.
=documentation=, =presentation-metadata=, =reference-implementation= and
=non-authoritative-analysis= are optional enrichment only.  The Agent may write
either class only through =.write-governance=; undeclared Slots, stale TLA+
digests and mismatched vertical payloads are rejected.

The migration assurance chain is concrete and stage-sensitive.  TLC checks the
=HealthcareStandardMigration= transition system; the Lean refinement binds the
exact TLA+ source digest; the impact contract rejects stale downstream proof;
and Cedar accepts only the exact human reviewer, migration action and migration
resource.  Review and admission accept qualified proof evidence.  Cutover
requires every mandatory Slot to be =admitted=, including a fresh Cedar permit.
The Case stores the Interface identity and relationship graph, while the
Healthcare Standard Feature owns the executable POO Interface.

The Case selects =AustraliaHealthcareStandardMigrationProfile= rather than the
general Australia care-delivery Profile.  This keeps migration governance
independent of Primary Care and Support at Home evidence while reusing the
same Healthcare, Evidence, Privacy and exact Standard objects.

The =post-operative-healing= Case currently selects three named compositions:

- =common=: evidence and privacy;
- =healthcare=: the Healthcare base vocabulary and healing semantics;
- =medication=: medication-safety Sources, Threat and Capability.

Case authors maintain only =profile-selection=, =source-declarations=,
=authorization-declarations=, =event-declarations=, =node-declarations= and =edge-declarations= declarations.  They do not
maintain reverse Profile indexes, Scenario Case registries or Impact lists.

* Personal care and healthy ageing across Regions

The =personal-care-coordination= Case models one continuous care journey
rather than treating an appointment as an isolated transaction.  Country and
jurisdiction are configuration, not Case identity.  The reusable care model is
owned by two Profiles:

- =PrimaryCareProfile= governs voluntary registration, the preferred practice
  and practitioner, provider eligibility, clinical triage and purpose-limited
  health-information sharing;
- =SupportAtHomeProfile= governs needs assessment, a reviewable decision, a
  person-centred support plan, an active referral credential and the person's
  choice of home-support provider.

The Case composes those Profiles with the common Evidence, Privacy and
Healthcare base Profiles, then selects =regions/australia= as a declarative
Region Profile.  Like selecting an AWS Region, replacing this Profile changes
the authority Sources and regional compliance deltas without copying the care
journey.  The UI is only the declarative POO surface:
=profile-selection= selects semantics, Case slots attest the evidence state,
=event-declarations= declares the causal trajectory, and =node-declarations= / =edge-declarations=
declare the enterprise relation graph.  A later =regions/canada= or
=regions/new-zealand= Profile can reuse the same Case and care Profiles.

flowchart LR
    R[Personal care request] --> T{Clinical triage}
    T -->|urgent or emergency| E[Leave routine booking path]
    T -->|routine| M[Voluntary primary-care registration]
    M --> G[Preferred GP consultation]
    G --> A[Care-needs assessment]
    A --> N[Reviewable eligibility decision]
    N --> P[Person-centred support plan]
    P --> C[Consumer selects provider]
    C --> H[Coordinated home-care service]
    H -. prospective .-> O[Independent-living outcome]
#+end_src

The routine path is admitted only when all reusable care observations and all
selected-Region observations are present.  Removing consent, provider
eligibility, triage, disclosure authority, assessment approval, plan binding,
referral-credential validity, consumer choice or either Australian program
verification independently blocks the Governance handoff.  Unsafe routine
booking and unconsented disclosure are explicit counterfactual branches; the
future independence outcome remains hypothesized rather than asserted.

This Case deliberately does not conflate specialist referrals with ordinary
primary-care and home-support coordination.  Specialist referral
validity is a later composable Profile with its own evidence and lifecycle.
Similarly, this structural and temporal receipt is not a clinical decision,
eligibility determination or production authorization.

The selected Australia Region owns content-local authority evidence under
=sources/regions/australia/=.  It currently cites the Australian Department of
Health and Aged Care MyMedicare patient, provider and 2026 program guidance;
My Aged Care assessment, Support at Home and care-management guidance; and
OAIC health-information guidance.  A future authority refresh therefore has a
traceable structural Impact through the Region Profile without changing the
portable Case.

* Standard two-layer causal trajectories

Correct handling, error handling and Impact are not conventions local to one
Healthcare Case.  The domain-neutral Temporal Causality core owns
=PooFlowCausalTrajectoryContract=, and =OntologyCase= exposes it through the
declarative =trajectory-declarations= slot.  Every contract separates two layers:

1. the operational layer declares one observed trigger, one ordered intended
   path and one or more error paths;
2. the Impact layer declares intended impacts separately from error impacts.

An intended path may contain only =observed=, =declared= or =derived= events.
An error path may contain only uncommitted =counterfactual= events.  Both kinds
of Impact may contain only uncommitted =hypothesized= events.  Every member must
resolve in the same event graph, intended and error paths must remain causally
connected, and each Impact must descend from the corresponding path.  The
framework evaluates these rules once in O(V + E + declared members) and places
typed assessments in the Case composition receipt.  A rejected trajectory
makes =trajectory-handoff-ready?= and the overall Governance handoff false.

#+begin_src mermaid
flowchart LR
    T[Observed trigger] --> I1[Intended step]
    I1 --> I2[Governance / independent review]
    I2 --> F[Declared future handoff]
    F -. hypothesized .-> PI[Intended Impact]
    I1 -. counterfactual .-> E1[Error branch]
    E1 -. counterfactual .-> E2[Unsafe effect]
    E2 -. hypothesized .-> EI[Error Impact]
#+end_src

The AI-assisted prescription and personal-care coordination Cases now consume
the same contract.  If automatic AI approval is changed from counterfactual to
observed/committed, native Case admission returns
=trajectory-contract-rejected=; it cannot silently become clinical fact.

* Reasoning relations

After a Case is admitted, =ontology-case-reasoning-graph= projects its accepted
POO values into the ordinary POO Flow Graph.  For several Cases,
=ontology-scenario-reasoning-graph= produces one Scenario graph.  The projection
contains these typed relations:

| Relation | Meaning | Modality |
|----------+---------+----------|
| =HAS_CASE= | Scenario owns the admitted Case boundary | declared |
| =USES_COMPOSITION= | Case selected a named composition | declared |
| =SELECTS_PROFILE= | Composition directly selected a Profile | declared |
| =IMPORTS_PROFILE= | Profile imports another Profile | declared |
| =HAS_EFFECTIVE_PROFILE= | Profile is in the accepted transitive closure | derived |
| =DECLARES_SOURCE= | Profile owns an authority Source | declared |
| =DECLARES_THREAT= | Profile owns a Governance Threat | declared |
| =DECLARES_CAPABILITY= | Profile owns an authorization Capability | declared |
| =HAS_EVENT= | Case declares one causal fact or candidate | declared |
| =CAUSAL_PARENT= | Event declares an explicit causal parent | event modality |

#+begin_src mermaid
flowchart LR
    S[Healthcare Scenario] -->|HAS_CASE| C[Post-operative healing Case]
    C -->|USES_COMPOSITION| CM[Medication composition]
    CM -->|SELECTS_PROFILE| MP[Medication Safety Profile]
    MP -->|IMPORTS_PROFILE| HP[Healthcare Base Profile]
    MP -->|IMPORTS_PROFILE| EP[Evidence Profile]
    MP -->|IMPORTS_PROFILE| PP[Privacy Profile]
    C -.->|HAS_EFFECTIVE_PROFILE / derived| MP
    MP -->|DECLARES_SOURCE| CS[Cedar policy Source]
    MP -->|DECLARES_THREAT| T[Contraindication evidence drift]
    MP -->|DECLARES_CAPABILITY| A[Administer medication]
#+end_src

The graph is a projection, not a second authority.  Its node payloads are the
same POO objects admitted in the composition receipt, and derived edges are
marked as derived.

* Structural Impact is reverse reasoning

Impact is intentionally not a user-authored =IMPACTS= edge.  Such an edge
would become stale whenever a Profile import or Case composition changed.
=ontology-reasoning-impact= instead walks the reverse dependency cone of an
exact graph node and returns an inert POO receipt containing the target,
dependency-node set and impacted Case identities.  This first receipt is
explicitly =snapshot-scoped-impact= with =scope: structural-snapshot=;
=temporal-impact-assessed?= and =release-authorized?= are both false.

For example, changing
=healthcare/medication/authorization/policy= reaches
=MedicationSafetyProfile= and then =PostOperativeHealingCase=.  The same
operation works for a Profile, Source, Threat or Capability node.  Adding a
second Healthcare Case to the Scenario graph makes it appear automatically if
its accepted Profile closure depends on that target.

Three standard GQL Sources live under =reasoning/=: Scenario/Case/Profile
relations, Profile Impact, and the prescription causal trajectory.
Gerbil-parser qualifies their ISO GQL syntax and byte-exact roundtrip.  The
current Lambda package does not execute GQL, so parser acceptance is not
presented as an execution receipt; native Scheme graph construction and Impact
evaluation are the executable authority today.
=healthcare-case-profile-property-source= now derives Scenario, Case, Profile,
=HAS_CASE= and =HAS_EFFECTIVE_PROFILE= property rows from that accepted graph.
It takes property values from the original POO payloads, checks relation
endpoints, and retains the exact content-bound GQL query object.  It does not
mint MRR type IDs, Arrow batches, CIDs, or a result-admission receipt.  POO
Flow's Runtime v0 boundary now validates and round-trips the typed
=PooFlowQueryExecutionCandidate= produced after execution, but it neither runs
MRR nor fabricates its receipt.  The MRR Data property worker can consume the
query after a runtime materializes and restores a verified snapshot; its Rust
adapter from MRR result admission to that versioned candidate remains the open
executable handoff.  The explicit =just check-healthcare-gql= gate reads the
Sources enumerated by =HealthcareCaseQualificationMetadata=; Lambda's native
test tree never takes a reverse dependency on gerbil-parser.

Structural dependency is only the first Impact dimension.  It answers which
Cases depend on a changed Profile or Source, but it does not claim that a drug
caused an observed condition, that a past administration can be rewritten, or
that a future adverse outcome will occur.  The temporal-causal extension is
specified in POO Flow RFC 161 as the =Temporal Causality= core.  It requires a
causal event graph, immutable event cuts, causal trajectories, present exposure,
bounded future horizons, counterfactual trajectories and an explicit unknown
frontier.  Impact Analysis is a derived view of that core, not its name.

The first executable slice is =wrong-prescription-review=.  Its =event-declarations=
slot declares seven events once: four observed and committed clinical facts,
one scheduled administration, one counterfactual corrected prescription and
one prospective reassessment.  The core seals all seven into one
=CausalEventGraph=, while the cut at logical position 4 contains only the four
committed facts.  Classification at horizon 6 returns separate past, current,
future and counterfactual identities.  Missing parent identities remain an
explicit =unknown-frontier= and prevent a complete classification.

The Scheme classification is structural and horizon-relative.  Its own
=assurance-closed?= and =release-authorized?= slots remain false.  The exact
=ai-assisted-antibiotic-prescription= qualification combines that native
classification with independent TLC model exhaustion and the Healthcare Lean
refinement; GQL remains a declared, parser-qualified analysis contract rather
than evidence in that safety closure.  The resulting assurance receipt is
closed but still not release-authorized.  Only its exact digest is admitted to
the fresh Cedar request.  Ordinary Scheme build and unit-test paths do not run
these cross-runtime qualification gates.

All Case-owned evidence locations and proof identities are declared once in
the POO object =HealthcareCaseQualificationMetadata=: contributor root, GQL
query objects, TLA+ source/config, TLC and Lean receipt paths, TLC worker
profile, Lean library/module/source digest and certification names.  Just
selects the capability to run; shell environment variables do not reconstruct
the Case semantics.

* Assurance and authorization flow

The relation graph explains composition and change propagation.  It does not
collapse the independent assurance roles:

#+begin_src mermaid
flowchart LR
    P[Gerbil POO declarations] --> R[Accepted relation graph]
    R --> I[Impact receipt]
    P --> T[TLA+ model]
    T --> TLC[TLC bounded temporal check]
    P --> L[Lean enterprise proof]
    P --> B[Cedar authority snapshot]
    B --> CR[Cedar Rust decision]
    B --> CL[Lean Cedar.Spec decision]
    CR --> H[Strict lockstep Runtime Host]
    CL --> H
    TLC --> H
    L --> H
    H --> E[Signed authorization evidence]
#+end_src

- Gerbil POO owns selected facts, Profiles and relation projection.
- GQL describes graph questions; it grants no authority.
- TLA+/TLC checks the bounded temporal transition system.
- Lean proves general Governance and enterprise-security obligations.
- Cedar Rust makes the production authorization decision.
- Lean =Cedar.Spec= supplies an independent executable semantic witness.
- The Runtime Host admits only matching, identity-bound evidence before an
  effect handoff.

Medication reconciliation, pharmacology review and AI review are independent
Profile-owned Governance slots.  Their inherited methods bind the actual POO
=self=, so a derived Profile retains its own threat-model identity.  At the
Cedar crossing, CLOS supplies explicit Medication, Pharmacology and AI
projection methods.  A Profile with declared threats and no applicable method
fails closed instead of disappearing through a default projection.  The exact
qualification binds the source-byte origin digest, canonical Profile bundle,
Governance assessment, subject snapshot, capability contract and all six Lean
certification names; placeholder digests are not admitted.

This separation lets an enterprise answer both questions without conflation:
"what changes are affected?" is an Impact query; "may this exact action run?"
is a current dual-engine authorization decision.
