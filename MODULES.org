#+title: POO contribution module contract

* Framework-owned module contract
The normative layout is documented by POO Flow in
=docs/10-19-design/10.06-poo-module-system/contribution-module-layout.org=.
Each module follows =types.ss=, =objects.ss=, =funs.ss=, =config.ss= and
=interface.ss=. The narrow =gerbil.pkg= declares native package identity only;
this repository does not implement its own layout checker, source registry,
build script, or =modules/init.ss=. POO Flow's
trusted contribution registry maps =lambda-episteme= and its public module
names to this repository's pinned source. POO Flow's =poo-flow-load-modules=
discovers direct =modules/<module-name>/= directories through their sole public
=interface.ss= entrypoints and constructs the
contributor and user source collections from repository roots. Its root-owned
contribution adapter projects those directories to one
ASP source stage per =modules/<name>/= tree. The shared deterministic tree walk
automatically supplies that module's Scheme files. No downstream =modules=
override, =all-gerbil-modules= call, contribution-owned source object, compiler,
scheduler, or cache is supplied. Imported helpers remain native =std/make=
dependencies and never need to be repeated in the build declaration.

* Module-owned tests
Executable tests live under =t/<owner>/<lane>/= and declare/export ordinary
=:std/test= suites with the same binding as the file basename. The single =unit-tests.ss= entry delegates
discovery and execution to =:clan/testing=.
Core policy and macro documentation live in POO Flow's
=contribution-test-ownership-rfc.org=, not a child-owned testing framework.

* Native POO module-writing standard
The five roles divide ownership rather than naming five interchangeable source
files:

- =types.ss= defines boundary predicates and actual nominal data contracts.
  =define-type= is appropriate for a closed wire or runtime boundary value; it
  must not simulate a prototype or class hierarchy.
- =objects.ss= owns POO prototypes, declaration projections and default method
  slots.  A user Profile exports one =.def= and declares =.import=,
  =.add-concept=, =.add-relation=, =.add-source=, =.add-rule= and =.add-query=
  as named POO slots.  The framework derives =imports=, =ontology=,
  =source-assets=, =terms=, =rules= and =queries= for existing algorithms.
  Behavior intrinsic to one Profile or Scenario uses =.defgeneric= slot
  dispatch, so a derived object replaces the slot directly.
- =funs.ss= owns pure closure, index, admission and projection functions.  It
  constructs an index once per Case and does not hide a second object system.
- =config.ss= only selects and composes Profiles and Standards.  It does not
  repeat stage or execution DSLs.
- =interface.ss= is the sole public re-export boundary.

A Case is a POO configuration object passed to a pure composition function.
Its user-facing file exports one Case declaration only: =.use-composition= owns
named Profile groups, =.add-source= owns named Case-local Sources, and =graph=
owns the declarative topology.  Native composition sequences, source sequences,
admission receipts and evaluations are framework-derived values; users do not
maintain parallel bindings for them.  CLOS
generic functions, class specializers and method bundles are introduced only
when two independently extensible axes actually meet, such as
Provider/executor by Profile, Scenario or Case.  Printing is already owned by
gerbil-poo's =(@method :wr object)= implementation: ordinary POO objects inherit
that protocol and customize its documented =.type .write-object=, =sexp= or
=write-object= slots.  A module may define =(@method :wr NewNominalType)= for a
new nominal runtime type, but must not redefine the upstream =object= method.
The admission test for =defmethod (@method generic Type)= is therefore: a real
nominal =Type= already exists, callers already speak =generic=, and the method
preserves that protocol.  A kind-tagged Profile, Scenario or Case does not pass
that test merely because a specialized printer would look convenient.

Ontology terms, relations, imports and policies are owned by POO Profile slots.
Case topology derives the POO Flow =graph= prototype directly: =.add-node= and
=.add-edge= are named POO object slots, not raw lists, RDF triples or a second
Graph builder.  The core Graph owns the lazy projection consumed by its existing
algorithms.
RDF is not a native-module dependency or a parallel semantic authority. Where
an external consumer genuinely requires RDF, a boundary adapter may derive it
one way from an accepted POO projection; the generated representation must not
be imported back to mutate or supersede Profile semantics.

Because =.o= evaluates a slot initializer in the new object's slot scope,
constructor parameters must not reuse the slot name.  Use names such as
=scenario-value= for =scenario:=.  The ASP Testing Profile evaluates source
admission over gxtest's prepared native graph and rejects a violation with
=self-referential-slot-initializer=.  It does not start an outer closure process
for every file; the per-test timeout remains containment for genuinely dynamic
hangs, not the primary diagnostic.

* POO Flow contribution build integration
POO Flow owns the default core PackageSpec, package namespace, root-level
contribution adapter, =std/make= handoff, and build environment. Contribution
production and test stages are independent from the core public closure but
install into the shared namespace. There is no contribution-owned package
manager, build script, compiler, scheduler, or artifact cache.
